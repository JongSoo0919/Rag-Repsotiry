# 2026.07.08 2일차

## 결론

오늘 작업으로 기본 RAG PoC는 완성됐다.

현재 가능한 동작은 다음과 같다.

```text
Confluence 문서 수집
→ 섹션 단위 chunking
→ Gemini embedding
→ Qdrant 저장
→ 사용자 질문 검색
→ Gemini LLM 답변 생성
```

즉, 문서 하나를 넣고 질문하면 문서 근거를 바탕으로 답변하는 최소 RAG 루프가 동작한다.

## 전체 흐름

RAG를 구성하려면 먼저 검색 가능한 지식 저장소가 필요하다.

이 프로젝트에서는 Qdrant를 Vector DB로 사용한다. Qdrant는 일반적인 문자열 검색 DB가 아니라, 문서와 질문을 vector로 변환한 뒤 vector 간 유사도를 계산해 관련 문서를 찾는다.

흐름은 다음과 같다.

```text
1. 문서 가져오기
2. 문서를 chunk로 나누기
3. chunk를 embedding하여 vector로 변환하기
4. vector와 payload를 Qdrant에 저장하기
5. 사용자 질문을 embedding하여 vector로 변환하기
6. Qdrant에서 질문 vector와 유사한 chunk vector 찾기
7. 찾은 chunk를 LLM context로 넣기
8. LLM이 질문에 맞는 답변 생성하기
```

## 내가 한 행동

### 1. Qdrant 준비

RAG를 만들기 위해서는 문서를 저장하고 검색할 Vector DB가 필요하다.

이번 PoC에서는 Qdrant를 Docker Compose로 띄웠다.

역할:

```text
문서 chunk의 vector 저장
사용자 질문 vector와 저장된 vector의 유사도 검색
관련 chunk point 반환
```

Qdrant에서의 구조는 다음과 같이 이해했다.

```text
collection = DB table
point = DB row
vector = 유사도 검색용 숫자 배열
payload = 사람이 읽을 수 있는 원문/메타데이터
```

현재 사용하는 collection:

```text
rag_poc_chunks
```

### 2. fetch_confluence_sample.py

파일:

```text
src/fetch_confluence_sample.py
```

역할:

```text
Confluence REST API를 호출해서 문서 본문을 가져온다.
가져온 HTML 본문을 텍스트로 변환한다.
변환한 텍스트를 data/sample.md에 저장한다.
```

현재 가져오는 문서:

```text
title: 대시보드 로그 시각화 이슈
space: SPACE
page_id: 123456789
```

흐름:

```text
CONFLUENCE_WIKI_URL, CONFLUENCE_USER_EMAIL, CONFLUENCE_ACCESS_TOKEN 읽기
→ page_id로 Confluence API 호출
→ body.storage HTML 가져오기
→ BeautifulSoup으로 HTML을 텍스트로 변환
→ data/sample.md 저장
```

`sample.md`로 저장하는 이유:

```text
PoC에서는 가져온 본문이 제대로 정제됐는지 직접 확인하기 위해 저장했다.
반드시 파일로 저장해야 하는 것은 아니다.
운영 구조에서는 Confluence에서 가져온 내용을 바로 chunking하고 Qdrant에 저장해도 된다.
```

현재는 학습과 검증을 위해 중간 산출물로 `data/sample.md`를 남기는 구조다.

### 3. chucker.py

파일:

```text
src/chucker.py
```

역할:

```text
data/sample.md를 읽는다.
문서를 섹션 단위로 나눈다.
chunk list를 반환한다.
```

처음에는 글자 수 기반 chunking을 생각했지만, 문서가 다음처럼 번호 섹션으로 잘 나뉘어 있었다.

```text
1. 개요
2. 증상
3. 원인 분석
4. 기존 설정
5. 조치 내용
6. 결과
7. 결론
```

그래서 정규식으로 섹션 제목을 찾아 chunk를 나누었다.

핵심 함수:

```python
split_by_sections(text)
```

중요한 점:

```text
chucker.py는 chunk를 DB에 저장하지 않는다.
chunk를 파일에 저장하지도 않는다.
sample.md를 읽어서 chunk list를 메모리에서 반환한다.
```

즉 `chucker.py`를 직접 실행하면 chunk가 출력되지만, 실제 RAG 저장 흐름에서는 `ingest.py`가 `split_by_sections()`를 호출해서 그 반환값을 사용한다.

### 4. ingest.py

파일:

```text
src/ingest.py
```

역할:

```text
sample.md를 읽는다.
chucker.py의 split_by_sections()로 chunk를 만든다.
각 chunk를 embedding API로 vector화한다.
Qdrant collection에 point로 저장한다.
```

현재 embedding 설정:

```text
EMBEDDING_API_KEY
EMBEDDING_API_MODEL=gemini-embedding-001
```

처음에는 OpenAI embedding 기준으로 만들었지만, 실제 키가 Gemini API Key였기 때문에 설정을 다음처럼 단순화했다.

```text
EMBEDDING_API_KEY
EMBEDDING_API_MODEL
```

모델 이름이 `gemini`로 시작하면 Gemini SDK를 사용하고, `text-embedding`으로 시작하면 OpenAI SDK를 사용하도록 구성했다.

저장되는 Qdrant point 구조:

```text
id
vector
payload.section
payload.text
payload.source_file
payload.chunk_index
```

`vector`는 Qdrant가 유사도 검색에 사용하는 숫자 배열이다.

`payload`는 LLM 답변 생성 때 context로 사용할 원문과 메타데이터다.

중복 저장 방지:

```text
처음에는 UUID로 point id를 생성했다.
그러면 ingest.py를 실행할 때마다 같은 chunk가 다른 id로 중복 저장될 수 있었다.
이후 chunk 내용 기반 hash id로 바꿔 같은 chunk는 같은 id를 갖도록 했다.
```

### 5. query.py 검색 단계

파일:

```text
src/query.py
```

역할 1:

```text
사용자 질문을 받는다.
질문을 embedding 모델로 vector화한다.
Qdrant에 질문 vector를 전달한다.
Qdrant가 유사한 chunk point를 찾아 반환한다.
```

SQL 비유:

```sql
SELESPACE *
FROM rag_poc_chunks
ORDER BY cosine_similarity(vector, question_vector) DESC
LIMIT 3;
```

실제로는 SQL이 아니라 Qdrant의 vector search API를 호출한다.

코드 흐름:

```text
question
→ create_embedding(question)
→ qdrant.query_points(...)
→ ScoredPoint 목록 반환
```

여기서 반환되는 것은 답변이 아니라 검색 결과다.

즉 이 단계만 있으면 chunk 원문이 그대로 출력된다.

### 6. query.py 답변 생성 단계

역할 2:

```text
Qdrant에서 찾은 chunk payload.text를 context로 묶는다.
사용자 질문과 context를 Gemini LLM에 전달한다.
LLM이 문서 근거 기반 답변을 생성한다.
```

현재 답변 생성 모델:

```text
LLM_API_MODEL=gemini-2.5-flash
```

별도 `LLM_API_KEY`가 없으면 기존 `EMBEDDING_API_KEY`를 같이 사용한다.

프롬프트 규칙:

```text
아래 context에 있는 내용만 근거로 답변한다.
context에 없는 내용은 "제공된 문서에서 확인할 수 없습니다."라고 답변한다.
답변은 한국어로 작성한다.
사용자의 질문에 직접 답한다.
답변 마지막에 참고한 section을 표시한다.
```

테스트 질문:

```text
Loki Dashboard에서 로그는 조회되는데 상단 시각화 패널이 0으로 나오는 이유가 뭐야?
```

생성된 답변 요지:

```text
Dashboard 시각화 패널은 namespace, app, container, level, stream label을 기준으로 집계한다.
기존 Alloy 설정에서는 특히 level, stream label이 생성되지 않았다.
따라서 Log Panel에는 로그가 보이지만, 시각화 패널의 집계 결과는 0으로 표시되었다.
```

## 오늘 이해한 개념

### Retrieval과 Generation

처음 `query.py`는 Qdrant 검색 결과를 그대로 출력했다.

이 상태는 RAG 중 Retrieval만 구현된 상태다.

```text
Retrieval = 관련 chunk를 찾는 단계
Generation = 찾은 chunk를 근거로 LLM이 답변하는 단계
```

오늘 작업으로 Generation까지 붙였다.

### 질문 검색 방식

사용자 질문이 들어오면 Qdrant에 문자열 그대로 검색하지 않는다.

흐름:

```text
사용자 질문
→ embedding 모델로 vector 변환
→ Qdrant에 question vector 전달
→ Qdrant가 저장된 point vector와 유사도 비교
→ 유사한 point 반환
```

즉 Qdrant는 문장을 이해하는 것이 아니라 숫자 vector의 유사도를 계산한다.

문장의 의미를 vector로 바꾸는 것은 embedding 모델의 역할이다.

### embedding 모델 일치

문서 chunk를 저장할 때 사용한 embedding 모델과 질문을 검색할 때 사용하는 embedding 모델은 같아야 한다.

현재 구조:

```text
문서 chunk embedding: gemini-embedding-001
질문 embedding: gemini-embedding-001
답변 생성 LLM: gemini-2.5-flash
```

답변 생성 LLM은 embedding 모델과 달라도 된다.

### vector size

vector size는 chunk 크기가 아니다.

```text
chunk size = 문서를 얼마나 크게 나눌지
vector size = embedding 결과 숫자 배열 길이
```

Gemini embedding 모델은 현재 3072 차원 vector를 생성한다.

Qdrant collection은 vector size가 고정된다. 같은 collection 안에는 같은 크기의 vector만 저장할 수 있다.

## 현재 완료 기준

아래 기준을 만족했으므로 기본 PoC는 완료로 본다.

```text
문서 하나를 가져온다.
문서를 chunk로 나눈다.
chunk를 embedding한다.
Qdrant에 저장한다.
질문하면 관련 chunk를 검색한다.
검색된 chunk를 근거로 LLM이 답변한다.
```

## 남은 작업

기본 PoC 이후 고도화 작업은 다음과 같다.

```text
1. payload metadata 개선
   title, page_id, source_url, space, version 추가

2. 없는 내용 질문 대응 개선
   score threshold를 두고 관련도가 낮으면 답변하지 않기

3. 중복 collection 정리
   OpenAI용으로 생긴 rag_poc_chunks와 Gemini용 rag_poc_chunks 정리

4. 다중 Confluence 문서 수집
   page_id 하나가 아니라 space/page tree 기준으로 여러 문서 수집

5. 증분 동기화
   page_id + version 기준으로 변경된 문서만 다시 embedding

6. API화
   FastAPI로 /ask endpoint 제공
```
