## 오늘 정리한 개념

### RAG

RAG는 LLM이 답변을 만들기 전에 외부 문서나 데이터베이스에서 관련 정보를 검색하고, 그 검색 결과를 LLM 입력에 넣어 답변하게 하는 구조다.

핵심 흐름:

```text
문서 수집
→ chunking
→ embedding
→ vector DB 저장
→ 질문 embedding
→ 유사 chunk 검색
→ LLM 답변 생성
```

### Chunking

Chunking은 문서를 검색 가능한 의미 단위로 자르는 것이다.

처음에는 글자 수 기반으로 나눴지만, 현재 문서처럼 번호 섹션이 명확하면 섹션 단위 chunking이 더 적합하다.

정리:

```text
글자 수 기반 chunking = PoC 확인용으로 쉬움
섹션 기반 chunking = 검색 품질과 출처 설명에 유리함
```

### Embedding

Embedding은 텍스트를 vector, 즉 숫자 배열로 변환하는 과정이다.

예:

```text
"Loki Dashboard 로그 시각화 패널이 0으로 표시된다"
→ [0.01, -0.24, 0.77, ...]
```

현재는 Gemini embedding 모델을 사용한다.

```text
gemini-embedding-001
```

### Vector size

Vector size는 chunk 크기가 아니라 embedding 결과 숫자 배열의 길이다.

예:

```text
OpenAI text-embedding-3-small: 1536
Gemini gemini-embedding-001: 3072
```

정리:

```text
chunk size = 원문을 얼마나 크게 자를지
vector size = embedding 결과 숫자 배열 길이
```

Qdrant collection은 vector size가 고정된다. 이유는 유사도 계산을 위해 같은 길이의 vector끼리 비교해야 하기 때문이다.

### Embedding 모델 일치 조건

문서를 저장할 때 사용한 embedding 모델과 질문을 검색할 때 사용할 embedding 모델은 같아야 한다.

정확한 표현:

```text
문서 chunk embedding 모델 = 질문 embedding 모델
```

답변 생성 LLM은 달라도 된다.

예:

```text
문서 embedding: gemini-embedding-001
질문 embedding: gemini-embedding-001
답변 생성: Gemini LLM 또는 GPT 등 가능
```

### Qdrant collection과 point

Qdrant의 collection은 DB의 table과 비슷하다.

Qdrant의 point는 DB의 row와 비슷하다.

구조:

```text
collection
└── point
    ├── id
    ├── vector
    └── payload
```

`vector`는 유사도 검색에 쓰이는 숫자 배열이다.

`payload`는 사람이 읽을 수 있는 메타데이터와 원문이다.

예:

```json
{
  "id": "uuid",
  "vector": [0.01, -0.24, 0.77],
  "payload": {
    "section": "3. 원인 분석",
    "text": "Dashboard Query에서 사용하는 Label이...",
    "chunk_index": 3
  }
}
```

Dashboard에서는 보통 payload가 먼저 보인다. vector는 너무 길기 때문에 기본 화면에서 잘 보이지 않을 수 있다.

## 오늘 했던 주요 질문과 답변

### Q. Qdrant를 설치하는 게 아니라 Docker Compose로 띄우는 게 나은가?

A. PoC는 Docker Compose가 낫다. 버전 고정, 삭제/재생성, 팀 공유가 쉽고 Dashboard도 `localhost:6333/dashboard`에서 볼 수 있다.

### Q. Confluence API로 샘플 문서 하나를 가져올 수 있나?

A. 가능하다. 실제 Confluence REST API를 사용해 페이지 1개를 가져와 `data/sample.md`로 저장했다.

### Q. sample.md로 꼭 저장해야 하나?

A. 운영에서는 꼭 파일 저장이 필요하지 않다. 하지만 PoC에서는 가져온 본문을 눈으로 확인하고, 같은 입력으로 반복 테스트하기 위해 저장하는 편이 좋다.

### Q. chunk를 출력만 하는데 어디에 저장되는가?

A. `chucker.py`를 직접 실행하면 출력만 한다. 실제 저장은 `ingest.py`가 `split_by_sections()` 함수를 호출해 chunk list를 메모리에서 받아 embedding 후 Qdrant에 저장한다.

### Q. 문단/섹션 기반 chunking이 좋은가?

A. 현재 문서는 번호 섹션이 명확하므로 섹션 기반 chunking이 더 좋다. 질문이 원인, 조치, 결과 중 어디에 해당하는지 검색하기 쉬워진다.

### Q. vector size는 chunk size와 같은가?

A. 아니다. chunk size는 원문 텍스트를 자르는 크기이고, vector size는 embedding 모델이 출력하는 숫자 배열 길이다.

### Q. vector size가 같으면 다른 embedding 모델끼리 비교해도 되는가?

A. 원칙적으로 안 된다. size가 같으면 계산은 가능할 수 있지만, embedding 공간의 의미 체계가 다르기 때문에 검색 품질이 망가질 수 있다.

### Q. embedding 모델과 답변 LLM도 같아야 하는가?

A. 아니다. 같아야 하는 것은 문서 embedding 모델과 질문 embedding 모델이다. 답변 생성 LLM은 달라도 된다.
